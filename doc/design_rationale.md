# 设计选择的理由 (Why)

本文解释 hgmCursorPager 为什么长这样 —— 每个刻意的取舍背后的原因。协议契约本身见
[pager_design.md](./pager_design.md)，改造过程中的踩坑见 [pager_design_notes.md](./pager_design_notes.md)。

这些不是"还没来得及做"，而是**刻意不做 / 刻意这么做**。下面逐条说清代价与收益。

## 为什么用游标分页, 不用 offset/limit 页码分页

传统 `LIMIT ? OFFSET ?` 的问题:

* **深翻页越来越慢**: `OFFSET 100000` 要求数据库先扫过并丢弃前 10 万行才能取到这一页。
  成本随页码线性增长，翻到后面卡死。游标版永远是 `WHERE key < ? ... LIMIT N`，走索引直接
  定位，任意页都是 O(pageSize)。
* **翻页期间增删会错位**: offset 是"位置序号"，如果翻页途中前面插入/删除了一条，后面每一页
  都会整体漂移一格 —— 用户会看到重复行或漏掉行。游标锚定在"某条具体记录的排序键"上，
  前面怎么增删都不影响"从这条之后往下取"。

代价: 不能跳到任意页码 ("直接去第 47 页")。但列表浏览场景几乎从不需要跳页，只需要
"下一页 / 上一页 / 回首页"，游标全能覆盖。

## 为什么不允许统计总数 (不 COUNT, 不显示总页数 / "第 X / Y 页")

这是最容易被质疑的一条，理由最硬:

1. **COUNT 的成本和分页本身不对称。** 取一页是 O(pageSize)，但 `COUNT(*)`（尤其带业务
   过滤 `WHERE`）往往要扫全表或全索引，是 O(N)。为了页脚一个"共 1234 条"，把一次廉价查询
   变成一次昂贵查询，大表上直接拖垮接口。分页的初衷就是"别碰全量"，COUNT 又把全量拉回来了。
2. **总数是个随时在变的瞬时值，显示出来反而误导。** 列表在用户翻页期间会被别人增删。
   显示"共 100 页"，用户翻到第 100 页却发现空了 / 少了，比不显示更让人困惑 ("是不是 bug?")。
   游标分页承认"数据是流动的"，只对"当前这一屏"负责。
3. **游标模型里根本没有"绝对页码"这个概念。** 游标是"相对位置"(比某条更新 / 更旧)，
   `currentPage` 只是前端点了几次"下一页"的计数，不是数据库里的第几页。既然没有绝对页码，
   "总页数"就无处安放，硬算出来也对不齐。
4. **交互上不需要。** "下一页 / 上一页 / 回首页 / 刷新" 这套动作完全不依赖总数。
   需要总数的通常是"随机跳页"，而那正是我们不支持的场景。
5. **维护总数的两条路都不划算。** 要么每次实时 COUNT（慢，见 1）；要么维护一个计数器
   （带来一致性负担和并发写热点，删除软删还得同步扣减）。为一个装饰性数字付这个代价不值。

所以直接不做。这是**范围收窄**，不是能力缺失 —— 换来的是"任意规模的列表，分页开销恒定"。

## 为什么"列表内部无停顿条件", 不适用评论树之类

协议假设列表是**一维线性、单一排序键**的序列。像评论树 (父子嵌套)、按分组折叠、
"未读分隔线"这种**在列表中间插入停顿 / 层级**的结构，用单一游标切不干净：一个 `(time, id)`
游标没法同时表达"我翻到了第 3 层第 2 个回复的下面"。硬套会导致游标语义歧义、切片重叠或丢失。

这类结构应该用别的模型 (整棵子树一次拉、或按 root 分页再各自展开)，不在本库范围内。
把适用边界讲清楚，比假装通用然后在树形数据上出诡异 bug 要诚实。

## 为什么 token 不透明 (opaque), 不把 cursor 字段暴露给前端

早期接口是 `{ CursorTime, CursorId, Direction }` 三件套直接摆在 API 上。改成一个不透明
`Token string` 后，收益最大:

* **后端换实现不动前端。** 想换排序键、加二级 tiebreaker、加业务过滤维度，只要 cursor
  struct 变一下，前端完全无感 —— 它只是"收到什么 token 就回传什么"。三件套时代任何后端
  内部调整都要前端跟着改。
* **前端不可能用错。** 前端不解析、不构造 token，也就没法把 CursorTime/CursorId 拼错、
  没法漏传 Direction。非法/过期 token 一律被后端 `Decode` 判成"第 1 页"，不报错。
* **接口收口干净。** 入参 `{ Token }`、出参 `{ Items, PrevToken, NextToken }`，
  跨列表长一个样，前端状态机可以完全通用 (见 `createCursorPager`)。

## 为什么 token 是裸 JSON, 不 base64, 不签名

* **不 base64**: token 走 POST JSON body，不是 URL query，不存在转义需求。base64 只是
  "看上去不透明"的审美，代价是体积 +33%、浏览器 Network 面板看不懂、调试摩擦增加。
  裸 JSON `{"Direction":"next","Cursor":{...}}` 直接可读，排查问题一眼看穿。
* **不签名**: 签名是为了防篡改越权。但游标 token 里只有"排序键位置"，用户伪造一个 token
  最多让自己翻到某个位置，**拿不到任何越权数据** —— 数据权限过滤在后端独立做，和 token 无关。
  为一个无法用于越权的东西加签名 (以及随之而来的密钥管理) 是纯负担。

## 为什么排序键必须是复合键 (业务时间 DESC, Id DESC)

只用业务时间 (如 CreateAt) 做游标切不干净: 同一秒/同一时刻可能插入多条，`WHERE time < ?`
会把"和游标同时间"的那些行**要么全丢要么全重**。加一个唯一的 `Id` 作 tiebreaker，游标变成
`(time, id)` 复合键，`time < ? OR (time = ? AND id < ?)` 才能在时间相等的那一批里切出
精确边界。两个方向都加 `Id` 的 `< / >`，前后翻都无重叠无丢失 (测试里专门覆盖了"12 条同
时间"的场景)。

## 为什么第 1 页的 token 固定是 ""

`""` 是一个刻意保留的特例: 它永远表示"最新一屏"。如果第 1 页也用一个具体 cursor token，
那么这个 token 会**老化** —— 用户拿着一个旧 token 回来，看到的是"当时的第 1 页"而不是
"现在的最新"。用 `""` 表示"给我最新的开头"，浏览器返回 / F5 / 分享链接后都能回到真正的
最新视角。

## 为什么容忍"末页正好 pageSize"时 NextToken 的 false-positive

后端判断"有没有下一页"的唯一依据是 `len(items) >= pageSize`。当最后一页**正好** pageSize 条
时，后端无法区分"这是末页"还是"后面还有"，于是 NextToken 仍非空 (假阳性)。

修它需要后端多查一条 (`LIMIT pageSize+1`) 来探测，给每次查询加成本。我们选择不修，改由前端
兜底: 用户点"下一页"拿到 0 条时，不前进、弹一句"已是最新一页, 数据已变化"、静默刷新当前页。
这是**把复杂度往前端压**的取舍 —— 后端保持每次只查 pageSize，前端加一个廉价的 0 条分支。

## 为什么不在 URL 里持久化页码 / token

不把 `currentPage` 或 token 写进 URL query。浏览器后退 / F5 会自然回到第 1 页 (最新视角)，
这是规范允许且符合直觉的: 分页是"临时浏览状态"，不是"可收藏的资源地址"。持久化 token 到 URL
反而会让用户收藏 / 分享出一个很快就过期、且暴露内部游标结构的链接。

## 为什么这套刻意"把复杂度往前端压"

后端规则越简单越好: 三个固定的 SQL case + 两条 token 计算规则，没有分支爆炸、没有探测查询、
没有计数维护。换来的边界情况 (末页假阳性、并发删除拿空、向前翻不足一页) 全部集中在前端状态机
里用统一的 5 个动作 (GoFirst/Refresh/GoNext/GoPrev + seq 兜底) 消化，并且被 22 个测试 case
钉死。后端简单 = 任何语言/任何存储都容易实现一份行为一致的后端；复杂度集中在一处 = 只需把
那一处测透。
